Moeen / مُعين: judge walkthrough

Moeen is a bounded AI agent loop. It picks up an eligible open-source issue, has an AI solver draft a fix and a test, checks the result with deterministic code, and opens a pull request only after a named human approves the exact diff. Every step goes into a public, hash-chained ledger.

What is simulated, in plain words
  • SANDBOX All real runs target Tarekchehahde/moeen-sandbox-shelter, a private repository we own with synthetic shelter-management code and deliberately seeded bugs. It is not a real humanitarian project, and no real project is touched.
  • MOCK HOST The run step uses an in-memory mock git host by design (a run never pushes). Only the approved open-pr step talks to GitHub.
  • SIMULATION The "Simulation" section and sim.json come from a StubEngine (scripted fixes) plus the mock host. No AI and no GitHub are involved. They show the failure paths (caps, kill switch, planted secrets, reject).
  • MOCK DATA The older concept demo at /portal/moeen-demo/ uses mock data throughout.
  • No organisation shown anywhere is a partner of Moeen.

2. How a run is triggered

Judge can do (in the browser)Operator does (on the agent box, CLI)
Open the live page, read status.json, ledger.json and sim.json, and follow the PR link. Judges can't start a run from the page: the page is static by design, with no backend and no buttons that spend AI budget. To see a live run, ask the team for a scheduled demo slot. 
# in the agent code repository (operator only)
python3 -m moeen status                 # counters, kill switch
python3 -m moeen --state-dir <state> run --issue 3    # one real run
python3 -m moeen kill on                # KILL switch: blocks every launch
python3 -m moeen kill off
Quotas enforced in code: 3 real runs a day, 12 per ISO week, one at a time, at most 2 open PRs, and no same-day retry after a timeout.

What happens next, in order: fetch the issue → eligibility rules (opt-in label, moeen:no veto, excluded topics) → caps → hand-off to the AI solver (Solver Moeen, deadline 20 min) → check #1 (scope, size, secrets, personal data) → tests (the regression test must fail before the fix and pass after; scored by code, not by the AI) → preflight (the patch must apply and pass on a fresh copy of the sandbox) → check #2 (everything shown or proposed) → awaiting approval.

3. The human approval gate

Only Tarek Chehade (GitHub Tarekchehahde) can approve, by typing exactly:

/approve <task_id> <sha8>      e.g. /approve t-20261024-1859-a72d 31b9e35a
/reject  <task_id> <reason>
  • sha8 is the first 8 hex digits of the diff's SHA-256. If the diff changes afterwards, the approval no longer matches and nothing happens.
  • Wrong author, wrong hash or a malformed line → ignored and logged. There is no auto-approve path in the code, and a test proves that open_pr() refuses without a valid approval.
  • Today Tarek types the line in the team chat and it's relayed to the operator. The ledger records the channel. Approving through a GitHub comment is planned, not built.
  • Only after approval does the code re-run the preflight, push a branch and open one pull request, in the sandbox repo only, with an AI-use disclosure.
